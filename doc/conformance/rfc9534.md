## Adversarial re-verification log (2026-07-22)

All three rows previously marked PROVISIONAL have been resolved by re-reading the cited RFC §3.2 text against the live RFC Editor page (paragraph by paragraph, in order) and by exhaustive `grep` re-verification of the relevant fields across `src/` and `tests/`:

- **9534-3.2-3**: CONFIRMED, with a sharper root cause than previously stated. The RFC's "if the Session-Sender knows..." conditional was checked as a possible "tied to an optional deployment model" excuse; it does not apply, because the CLI field to carry that knowledge (`--reflector-member-link-id`) already exists and is not role-gated — it is simply never read by `sender.rs`. Corrected the line references (`sender.rs:385-386`, not `:382`) and the prior claim that no such CLI field exists at all.
- **9534-3.2-11 / 9534-3.2-12**: CONFIRMED. Unlike 9534-3.2-3, this MUST has no conditional qualifier in the RFC text, and at least one validation (session-local consistency of the reflected Reflector Micro-session ID) is implementable with zero additional configuration — so the "optional deployment model" defense does not apply here either. No code path performs any such check.

No row in this file changed Status as a result of this pass; all three remain Gap. Summary counts are therefore unchanged from the pre-adversarial-pass total.

**Update (Chunk G-fix, round 1, same day):** the zero-config gap identified above for 9534-3.2-11 — "at least one validation ... is implementable with zero additional configuration ... No code path performs any such check" — has been closed: `validate_reflected_tlvs` now latches the first validly-received reply's Reflector Micro-session ID as the expected value when no pre-known `--reflector-member-link-id` is configured, and rejects later replies that diverge from it via the same `ReflectorMsidMismatch` path used for the pre-known case (9534-3.2-12). See the row 3.2-11 evidence above for file:line references and test names. This supersedes the "remain Gap" conclusion for 9534-3.2-11 / 9534-3.2-12 stated above; row Status was already recorded as Compliant in the table and that status is now fully substantiated for the unconditional MUST rather than only the pre-known-configuration reading.

- The mapping of a micro STAMP session to member-link identifiers "can be configured by augmenting the STAMP YANG [STAMP-YANG]" (§3.2) uses no RFC 2119 keyword and is explicitly out of this document's scope ("The detailed augmentation is not in the scope of this document"); no row created. (STAMP YANG itself is separately tracked as expired/no-standard in this project's standards notes.)
- The stateless/stateful characterization in §3.2 ("the micro STAMP-Test does not introduce any additional state to STAMP") uses no RFC 2119 keyword; observationally consistent with the implementation (`apply_micro_session_id` and `validate_reflected_tlvs` are both pure functions over the received packet plus static configuration, with no persistent per-micro-session state), but not scored as a separate clause per the extraction methodology.
