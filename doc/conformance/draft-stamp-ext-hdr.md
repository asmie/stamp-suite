> **Codepoint note.** IANA has not yet allocated TBA1/TBA2/TBA3. This tree uses
> experimental stand-ins: **Type 246** = Reflected IPv6 Extension Header Data
> (TBA1), **Type 247** = Reflected Fixed Header Data (TBA2), **Sub-TLV Type
> 240** = IPv6 Extension Header Control (TBA3), under the `Reflected Test
> Packet Control` TLV (Type 12, draft-ietf-ippm-asymmetrical-pkts-14). All
> three are live-fire values, not registered; interop with any other
> implementation requires agreement on these numbers pending IANA action.
>
> **-11 rework note.** The -11 revision split each of TLV 246/247's Value
> field into a fixed 4-octet **Requested** field (a disambiguation selector,
> left as received) and a **Reflected** field of `Length - 4` octets (the
> matched header's bytes from offset 4 onward). This creates an internal
> tension the draft leaves implicit: §5.1/§5.2 phrase the all-zeros-Requested
> case as "match the **first** length-matching header," which is a
> stateless per-TLV rule, while §3.1 rule 2 / §3.2 rule 2 require multiple
> same-type TLVs to pair **positionally** with the wire-order chain of
> headers (1st TLV ↔ 1st header, 2nd TLV ↔ 2nd header, ...) — a naive
> "first match" applied independently to each TLV would instead pair every
> such TLV with the same first header. This implementation reconciles the
> two with **first-fit-with-consumption**: each matched captured header is
> marked consumed so a later TLV of the same value-length skips it,
> yielding §3.1/§3.2 ordering while still honouring §5.1/§5.2's per-TLV
> first-fit rule. See `src/tlv/list/processing.rs` (`apply_reflected_ext`,
> doc comment above `process_reflected_headers`) and the rows for
> ext-hdr-3.1-6 / ext-hdr-5.1-C below, which carry this note explicitly.
