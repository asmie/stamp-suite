# RFC 8972 conformance — stamp-suite

Revision frozen: RFC 8972, "Simple Two-Way Active Measurement Protocol Optional Extensions" (January 2021) (verified 2026-07-22 against https://www.rfc-editor.org/rfc/rfc8972.html)

**Errata note (verified against the RFC Editor errata tracker on 2026-07-22, https://www.rfc-editor.org/errata/eid8199 and https://www.rfc-editor.org/errata/eid8339, both Status: Verified):**

- **Erratum 8199** (against §4.4): the published text says the reflector "MUST copy the value of the DSCP and ECN fields of the IP header of the received STAMP test packet into the DSCP2 field in the reflected test packet" (ECN's destination field is missing). The verified correction reads: "...into the DSCP2 and ECN fields, respectively, in the reflected test packet." This matrix evaluates §4.4 against the **corrected** text (row RFC8972-4.4-7).
- **Erratum 8339** (against §4.7): the published text says "The Session-Reflector MUST validate the Length value of the STAMP test packet" (there is no such field on the whole packet). The verified correction reads: "The Session-Reflector MUST validate the Length value of the Follow-Up Telemetry TLV in that STAMP test packet." This matrix evaluates §4.7 against the **corrected** text (row RFC8972-4.7-5).

Both corrections are treated as amending the base text per this matrix's brief; rows derived from the corrected wording are marked with an "[erratum NNNN]" tag in the Clause column.

## Report notes

* §1 (Introduction), §2 (Conventions/Acronyms/Requirements Language boilerplate), and the informative sub-paragraphs of §4.2.2/§4.6/§4.7 that use only lowercase "will"/"can"/"might" (no RFC 2119 keyword) contributed no clauses and are excluded from the row count, per the method's "MUST/MUST NOT/SHOULD/SHOULD NOT/MAY" extraction rule.
* Two related **Gap** clusters dominate the remaining confirmed findings and each traces to one root cause, not many independent defects: (a) §3's SSID-based session provisioning/discard (RFC8972-3-6/-7/-8) — the reflector is architecturally a general-purpose, accept-any-source responder with no per-session admission table (interpretive caveat: the binding MUSTs apply to a reflector "that supports this specification," and §3 places the *means* of provisioning out of scope, so a stateless accept-any reflector is a defensible reading); (b) §4's sender-side U/M/I processing gates (RFC8972-4-17/-18/-19, RFC8972-4.8-16/-17) — re-confirmed to bind the Session-Sender's reply path verbatim, and the only live TLV-value consumer there (Micro-Session-ID) reads its value before any flag or HMAC result is consulted (security-relevant: forged/integrity-failed TLV data can reach the session-binding check).
* **§4.6's Access Report retransmission timer (RFC8972-4.6-9 through -14) — Gap→Compliant (Chunk F1, 2026-07-22).** A pure, socket-free `AccessReportRetransmitState` state machine (`src/sender.rs`) now arms a retransmission timer on the packet carrying the Access Report TLV, disarms it when a reflected packet echoes a recognized/intact copy of the TLV (`"AccessReport:ack"` marker gated by the same U/M/I/HMAC flow that already protects Micro-Session-ID consumption), retransmits on expiry up to a configurable retry budget (default 4, RFC's SHOULD), and aborts (logs + counts, measurement unaffected) once exhausted. Both the timer value and retry count are independently controllable (`--access-report-timeout`, `--access-report-retries`), satisfying the co-located MUST. Reading adopted for the "attach every packet vs. event-driven" question the brief raised: the TLV is now attached only on the original send and on each retransmission — not unconditionally on every outgoing packet as before — since §4.6 frames the report and its retransmission as one bounded delivery procedure per event, and the RFC's own "MUST retransmit the STAMP test packet that contains the Access Report TLV" phrasing implies the TLV's presence is tied to that procedure's attempts, not to every packet in the session.
  * **Fix round 1 (2026-07-22): the state machine was only ever driven from inside the main send loop.** Reviewer-caught defect: `tick()` was called once per send-loop iteration but never again afterward, so any run shorter than the full retry budget (`access_report_timeout * (1 + retries)`, up to 15s at defaults — trivially true for the common `--count 1`) returned with the state machine still `Armed` — reported `Pending` — without a single retransmission ever having had the chance to fire, even though this row already claimed Compliant. Fixed by extending the sender's post-loop wait phase (`sender.rs:1007-1201`) to keep ticking/sending/receiving until the procedure reaches `Acknowledged` or `Aborted`, inherently bounded by the retry budget itself; a no-op when `--access-report` is unset. See RFC8972-4.6-11/-12 rows for the updated evidence and new tests, and `doc/usage.md`'s TLV-driven sender features section for the resulting run-time-extension caveat.
* **Timestamp Information TLV (RFC8972-4.3-2/-5/-6) — post adversarial re-verification (2026-07-22):** the cluster splits into one hard MUST violation and two reclassified soft findings. RFC8972-4.3-2 (sender) is a **CONFIRMED MUST NOT/MUST Gap**: §4.3 verbatim says the sender "MUST NOT fill any information fields except ... Flags, Type, and Length. All other fields MUST be filled with zeroes," and since *all four* value bytes are defined to characterize the Session-Reflector (ingress T2 / egress T3) there is no field for the sender's own clock — the interpretive "sender fills its own info" reading was refuted, and `TimestampInfoTlv::new` writing the sender's clock into `sync_src_in`/`timestamp_in` is a real defect. In contrast RFC8972-4.3-5/-6 (reflector filling the "In" fields) were **downgraded Gap→Partial**: the full §4.3 text imposes *no* explicit reflector-fill MUST for any field — the field definitions are purely descriptive with no RFC 2119 keyword — so the reflector not populating its ingress info is a telemetry-completeness shortfall, not a MUST violation. Net: the single most consequential defect is now the sender-side 4.3-2, not the reflector-side pair.
* Location TLV Source-MAC/EUI-48 rows (RFC8972-4.2.1-5, RFC8972-4.2.2-4/-5) are marked N-A/Compliant-with-note rather than Gap: neither backend (`nix.rs`, `pnet.rs`) has any way to observe an Ethernet frame's source MAC address from a UDP socket, so the RFC's own explicit "does not have the Source MAC Address → zero the EUI-64 field" fallback is the only reachable branch, and the implementation takes it correctly and consistently.
* The reflector's unconditional addition of an HMAC TLV to authenticated/keyed replies regardless of whether the request carried one (RFC8972-4.8-1) is cited as **Compliant-with-note**, per the documented adjudication in `src/tlv/list/mod.rs`'s `set_hmac_response` doc comment, rather than scored as a deviation.
