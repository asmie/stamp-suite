## Adversarial re-verification log (2026-07-22)

Both rows previously marked PROVISIONAL have been resolved by re-reading the cited RFC text against the live RFC Editor page and by re-reading the nix and pnet send paths in full:

- **9503-3-1**: CONFIRMED, and extended — verified that pnet's send path is a plain wildcard `UdpSocket`/`send_to()` (not a raw-IP-header-constructing path as hypothesized), so both backends share the identical gap; no per-backend split was needed. Status unchanged (Partial, SHOULD-level).
- **9503-4-3**: RECLASSIFIED from Partial to Compliant — §4.1 permits (MAY) a Return Address and a Segment List Sub-TLV together but defines no precedence between them when both are present, so the Reflector's deterministic choice of one is a legitimate implementation decision, not a gap. The previous evidence text's specific behavioral claim was also corrected to describe the shipped default policy (`--return-path-allow-alternate=false`) accurately: the SRv6 branch is currently unreachable whenever a Return Address sub-TLV is also present, regardless of whether address override is allowed — noted as a design-quality observation, not a Gap.

## Notes on excluded / non-extracted text
- §3's descriptive sentence "In this case, the Session-Reflector does not use the received Destination Node Address as the Source Address" and §4.1.1's descriptive behaviour sentences ("the Session-Reflector does not transmit a reply test packet...and terminates", "the Session-Reflector transmits the reply test packet over the same incoming link...") carry no RFC 2119 keyword of their own; their substance is covered by the keyworded U-flag/ignore-other-sub-TLVs rows adjacent to them (9503-3-3, 9503-4.1.1-2, 9503-4.1.1-3).
- §4.1.2's "The STAMP reply test packet may be transmitted to the Session-Sender to the specified Return Address ... instead of ... the Source Address" uses lowercase, non-keyword "may" describing the mechanism's purpose; its behaviour is scored under the general Return Path processing rows (9503-4-3, 9503-4-4) and the Security Considerations MAY row (9503-6-2), not as its own row.
- §4.1.1's own Type/Length/flag-position figure text ("Type (value 1)...", "Reply Request Flag at bit 31...") is format definition, not a separate normative clause; verified structurally via `src/tlv/typed/return_path.rs` and `RETURN_PATH_CONTROL_CODE_SIZE` in `src/tlv/core.rs`.
- Appendix A (informative example of tunnel-decap addressing motivating the Destination Node Address TLV) and the Acknowledgments/Contributors/Authors' Addresses sections contain no normative text and were not extracted.
- The "same incoming link" reply behaviour for Control Code `0x1` (9503-4.1.1-3) is honoured only in the sense that a normal `send_to(src_addr)` on a single-homed/directly-connected reflector trivially egresses over the ingress link; there is no explicit `SO_BINDTODEVICE`-style interface pinning in `nix.rs`/`pnet.rs` to force this on a multi-homed reflector where the default route could differ from the ingress interface. This is documented in the code itself (`processing.rs:325-335`) as a deliberate "decide at send time, not parse time" deferral, and no U-flag/Gap is asserted here because the RFC does not give the reflector a way to detect the mismatch at packet-processing time either — flagged for awareness rather than scored as a distinct clause.
