# Live UDP baseline — 2026-09-10

This is a live UDP baseline, not a before/after comparison or capacity limit.
See [benchmark methodology](../benchmarks.md) for accounting definitions and
reproduction commands. Full build/run commands, metadata and raw trials are retained in the
[standalone JSON artifact](2026-09-10-live-udp.json).

## Setup

- Production revision `2c8bb83222b1c7e0041d72c35a7df5f09cf6f861`, plus the benchmark
  example. The benchmark added no production runtime changes.
- Rust 1.98.1, x86_64-unknown-linux-gnu, locked release builds. Default features
  select nix; pnet uses `--no-default-features --features ttl-pnet`.
- Intel Core Ultra 9 275HX, WSL2 Linux 6.18.33.2, inherited CPUs 0–23,
  two Tokio workers. Shared workstation, no CPU pinning or frequency control.
  Other host load was not controlled; runs were sequential, without concurrent
  project builds/tests. This is not bare-metal or cross-platform evidence.
- Three fresh-process trials per case: 3 s load, 500 ms drain, two 2 s idle
  samples. Loopback, one measured session, 44-byte open / 112-byte auth packets,
  no TLVs, hardware/kernel timestamping off. Nix used the host network namespace;
  pnet used a private user/network namespace with loopback up and CAP_NET_RAW.
  Do not attribute backend differences solely to implementation cost.
- JSON records each binary's SHA-256, generator features, complete reflector
  command, raw CPU ticks and observed wall intervals. Tick resolution is 10 ms.

Across 54 trials, 6,028,465 successful sends were recorded. There were 0 invalid replies, 899,925 duplicates and 0 unique out-of-order replies. The largest idle sample was 2 ticks over approximately two seconds. All post-idle probes succeeded.

Pnet loopback produced 899,925 duplicate replies across 899,925 successful sends:
one duplicate for each request.
Duplicates are excluded from unique throughput and loss. Capturing both loopback
directions is a possible cause, but these measurements do not establish it. The
extra work limits direct CPU comparisons with nix.
The nix trials recorded no duplicates.

The 5,000 and 25,000 pps nix trials received every successfully sent request
within the drain window. Some 100,000 pps trials lost packets despite nearly
meeting the requested send rate. Loss location is not known: these observations
include both UDP directions and the generator's receive queue. Repeat on a
controlled host and inspect queues/profiling before attributing a bottleneck.

The pacing, validation and CPU costs of this generator are part of the recorded
setup. Batching changes instantaneous load; three-second samples and tick
quantization limit precision. A zero-tick idle interval does not prove zero CPU
work. These results do not cover real NICs, multi-session contention, burst/TLV
workloads, kernel/hardware timestamps, latency, or platform interoperability.
No throughput threshold is used as a CI correctness gate.
